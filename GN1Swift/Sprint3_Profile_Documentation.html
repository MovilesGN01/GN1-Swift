2 · Authenticated User Integration

The Profile screen is fully gated — no data loads without a logged-in Firebase user.

UserSession.shared.userId
Every data operation starts with guard let userId = UserSession.shared.userId else { return }. If the user is not authenticated, the entire load is aborted.
Firebase Auth Logout
try? Auth.auth().signOut() then sets isLoggedIn = false, which the parent view uses to navigate back to the login screen.
Firestore User Document
Data is read from users/{userId} — the userId comes directly from the authenticated Firebase session, not from user input.
Storage Security
Profile photos are uploaded to profile_images/{userId}.jpg. Firebase Storage rules enforce that only request.auth.uid == userId can write.
// ProfileViewModel.swift — loadProfile() gated by auth
func loadProfile() {
    guard let userId = UserSession.shared.userId else { return }
    // all subsequent operations use this userId
}

// ProfileView.swift — logout clears auth state
private func logout() {
    try? Auth.auth().signOut()
    isLoggedIn = false
}

Rubric: Protected View (5 pts each) — The Profile view is protected. It only shows data for the currently authenticated user, and logout navigates away immediately.

3 · Business Question 2 (BQ2)

How much faster is loading from cache compared to loading from Firebase Firestore?

BQ2 asks: "Is it worth caching user profile data locally — and by how much does it improve load time?"

Cached Load Time
Time to read from any local layer (NSCache, CoreData, UserDefaults, JSON). Typically 0.5–5 ms. Measured with Date() before and after the background I/O block.
Network Load Time
Full round-trip to Firebase Firestore. Typically 200–800 ms. Measured from the moment Task{} starts until getDocument returns.
Improvement %
Percentage improvement of cache over network. Displayed in the Performance Analytics card with animated progress bar.

Formula

// ProfileViewModel.swift — computeImprovement()
improvementPercentage = ((networkLoadTime - cachedLoadTime) / networkLoadTime) * 100

// Example: network=450ms, cached=2ms → ((450-2)/450)*100 = 99.6%

Timing code

// Cache timing
let cacheStart = Date()
DispatchQueue.global(qos: .background).async {
    // ... read all 4 local layers ...
    let cacheMs = Date().timeIntervalSince(cacheStart) * 1000
    DispatchQueue.main.async { self.cachedLoadTime = cacheMs }
}

// Network timing
let networkStart = Date()
Task {
    // ... await Firestore.getDocument ...
    let networkMs = Date().timeIntervalSince(networkStart) * 1000
    await MainActor.run {
        self.networkLoadTime = networkMs
        self.computeImprovement()
    }
}

4 · Multi-threading & Concurrency

Two distinct threading strategies used in the same ViewModel.

Strategy A — GCD (DispatchQueue)

Used in loadProfile() for reading local cache layers.

// Move to I/O thread
DispatchQueue.global(qos: .background)
  .async { [weak self] in
    // read NSCache, CoreData,
    // UserDefaults, JSON file

    // Back to main for UI
    DispatchQueue.main.async {
        self.cachedLoadTime = cacheMs
        self.userName = ...
    }
}

Strategy B — Swift Concurrency

Used in fetchFromFirebaseAsync() for network.

Task { [weak self] in
    let snap = try await
      withCheckedThrowingContinuation { cont in
        db.getDocument { snap, err in
          if let err { cont.resume(throwing: err) }
          else { cont.resume(returning: snap!) }
        }
    }
    await MainActor.run { self.userName = ... }
}

Update @Published UI properties (after cache)MainDispatchQueue.main.async

Key difference: GCD is the older, lower-level API using closures and queue dispatching. Swift Concurrency is modern — structured, with compiler-enforced actor isolation. Both are used intentionally to demonstrate knowledge of both paradigms.

    let obj = NSEntityDescription.insertNewObject(forEntityName: "CachedProfile", into: ctx)

    defaults.set(email,  forKey: keyEmail)

File

        "savedAt": Date().timeIntervalSince1970]

6 · Caching Strategy — NSCache + LRU

Two NSCache instances with explicit memory budgets and LRU eviction.

Profile Data Cache

// ProfileCacheService.swift
private let cache = NSCache<NSString, NSDictionary>()

cache.countLimit     = 10
cache.totalCostLimit = 1 * 1024 * 1024  // 1 MB
LRU Eviction
When countLimit=10 is reached, NSCache automatically evicts the Least Recently Used profile entry.

Image Cache (KingFisher-style)

// ProfileImageCache.swift
private let cache = NSCache<NSString, UIImage>()

cache.countLimit     = 20
cache.totalCostLimit = 10 * 1024 * 1024  // 10 MB

// Per-image RGBA cost
let cost = Int(image.size.width * image.size.height * 4)
Per-image Cost
Each image is stored with its RGBA memory cost (w×h×4 bytes). NSCache evicts when total exceeds 10MB.

4+1 Layer Cache Chain

1NSCacheProfileCacheService~0.01 msSession onlyLRU (auto)

ℹ️
How it works: Try Layer 1 → on miss, try Layer 2 → Layer 3 → Layer 4. First hit wins. Firebase (Layer 5) always runs concurrently in background regardless of cache hit. The dataSource chip in the UI shows which layer was hit.

7 · Eventual Connectivity

The app never shows a blank screen — graceful degradation through cached data.

Scenario 1: First Launch (Online)
All 4 cache layers miss → Firebase loads → data shown and saved to all 4 layers for future use.
Scenario 2: Subsequent Launch (Online)
Cache hits → data shown immediately → Firebase refreshes in background → UI silently updates.
Scenario 3: Offline
Cache hits → data shown → Firebase throws error → isOffline = true → orange OfflineBanner shows.

11 · Viva Q&A — 15 Questions & Answers

The most likely questions from your examiner with clear, concise answers.

Q1: Why did you use two threading strategies instead of just one?
Because the rubric requires demonstrating knowledge of both paradigms. GCD (DispatchQueue) is the classical iOS approach — explicit, queue-based, uses closures. Swift Concurrency (Task/async-await) is the modern approach — structured, cleaner error handling with try/catch, and compiler-enforced actor isolation. Using both in the same ViewModel shows I understand when each is appropriate.
Q2: What is LRU eviction and how does NSCache implement it?
LRU stands for Least Recently Used. When the cache reaches its capacity, it evicts the item not accessed for the longest time. NSCache implements this automatically — you set countLimit=10 and it handles eviction internally. For the image cache I also set a per-object cost (width × height × 4 bytes = RGBA footprint) so NSCache can evict by memory size, not just count.
Q3: Why did you create a separate CoreData stack instead of using the existing one?
The existing Rides NSPersistentContainer has its own entity model. If I added a CachedProfile entity and something went wrong with the migration, it could break the Rides feature. By creating ProfilePersistenceController with its own NSPersistentContainer("ProfileModel"), the two stacks are isolated — separate SQLite files, separate contexts, no shared state.
Q4: What is withCheckedThrowingContinuation and why did you use it?
Firestore's getDocument uses a completion callback (callback-based API), but our function is async. withCheckedThrowingContinuation creates a bridge — it pauses the async function and gives you a continuation. You call resume(returning:) on success or resume(throwing:) on error. "Checked" means Swift crashes if you forget to resume, preventing silent hangs.
Q5: What is the difference between DispatchQueue.main.async and await MainActor.run?
Both dispatch work to the main thread. DispatchQueue.main.async is GCD — enqueues a closure on the main queue, works anywhere. await MainActor.run is Swift Concurrency — used inside async functions, benefits from compiler actor isolation checks. Same end result, different paradigms.
Q6: Why does the OfflineBanner show even though cached data was loaded?
Because isOffline means "Firebase is unreachable right now" — not "we have no data." The user might be seeing stale cached data from hours ago. The banner is honest UX: data is available but may be outdated. This is the core of Eventual Connectivity — show available data, be transparent about its freshness.
Q7: How does the BQ2 improvement percentage formula work?
improvementPercentage = ((networkLoadTime - cachedLoadTime) / networkLoadTime) × 100. Example: network=450ms, cached=2ms → ((450-2)/450)×100 = 99.6%. The cache is 99.6% faster. If negative, cache was slower (the UI shows an orange down-arrow for that case).
Q8: Why did you use .atomic when writing to files?
.atomic writes data to a temporary file first, then renames it to the target path. This is crash-safe — if the app crashes mid-write, the original file is untouched. Without .atomic, a crash during write would leave a corrupt partial file.
Q9: How does PhotosPicker avoid needing photo library permission?
PhotosPicker (iOS 16+, PhotosUI framework) uses Apple's system photo picker which runs in a separate OS process. The user grants access inside that system UI, and only the selected photo data is returned. The app never gets direct library access, so no NSPhotoLibraryUsageDescription is needed.
Q10: What is the 4-layer cache chain and which is fastest?
Layer 1: NSCache (~0.01ms, session only). Layer 2: CoreData (~1-3ms, persistent SQLite). Layer 3: UserDefaults (~0.5ms, persistent plist). Layer 4: JSON file (~2-5ms, persistent Documents/). NSCache is fastest because it's pure RAM with no I/O or deserialization. The tradeoff is it doesn't survive app restarts.
Q11: Why does ProfileImageCache store images with a cost value?
NSCache supports eviction by memory cost (totalCostLimit). By setting cost = width × height × 4 bytes (RGBA size), NSCache can evict based on actual memory usage. A 2000×2000 photo uses 16MB and evicts fast. A small thumbnail uses 20KB and stays. This is exactly how KingFisher and SDWebImage work.
Q12: How is data secured — what prevents one user reading another's profile?
Three layers: (1) Firestore path uses the authenticated user's UID — the app fetches its own document only. (2) Firestore security rules should enforce request.auth.uid == userId for reads/writes. (3) Firebase Storage rules enforce the same for photos. Local caches are in iOS's private app sandbox — no other app can read them.
Q13: What is QoS .background and why did you choose it for cache reads?
QoS (Quality of Service) tells the OS how urgently the work needs CPU time. .background is the lowest priority. I used it for cache reads because the UI shows a loading state — the work doesn't need to compete with animations or touch events. .userInteractive would waste CPU cycles on work the user isn't immediately blocked by.
Q14: Why is UserDefaults layer 3 and not layer 1 in the cache chain?
NSCache is layer 1 because it's pure RAM — no serialization, instant. UserDefaults needs to read a plist file and deserialize it, which is slower. CoreData gets layer 2 priority over UserDefaults because it stores the full profile including the role field, which UserDefaults doesn't. The chain is ordered by speed and data completeness.
Q15: How does optimistic update work for the profile photo?
When the user picks a photo, profileImage = image is set immediately on the main thread — the avatar updates before any upload starts. This is called an optimistic update: we assume the upload will succeed and show the result early. If the upload fails, the worst case is the photo shows locally but isn't on other devices. The local file save (step 2) ensures it persists even if Firebase is unreachable.

12 · Glossary (30 Terms)

Key terms for your viva — concise definitions.

NSCache
Apple's in-memory cache with automatic LRU eviction under memory pressure. Thread-safe, supports countLimit and totalCostLimit.
LRU (Least Recently Used)
Eviction policy that removes the item not accessed for the longest time when the cache is full.
DispatchQueue
GCD abstraction for managing concurrent work. .global() for background I/O, .main for UI updates.
GCD (Grand Central Dispatch)
Apple's C-based threading library. Manages work queues and thread pools for concurrent execution.
Task { }
Swift Concurrency primitive that creates a new async execution context on the cooperative thread pool.
async/await
Swift's structured concurrency syntax. async marks a suspendable function; await pauses the caller until the result is ready.
MainActor
Swift actor that serializes execution on the main thread. await MainActor.run{} is the async equivalent of DispatchQueue.main.async.
withCheckedThrowingContinuation
Bridges callback APIs to async/await. Pauses the async function; caller resumes it via continuation.resume().
CoreData
Apple's object-relational persistence framework. NSManagedObject, NSPersistentContainer, NSFetchRequest, backed by SQLite.
NSPersistentContainer
CoreData stack wrapper that creates the SQLite store, model, and contexts. Named "ProfileModel" in this project.
NSManagedObjectContext
CoreData scratchpad for operations. viewContext for reads, backgroundContext() for writes.
UserDefaults
Key-value store backed by a plist file. Suitable for small preference values. Persists across app launches.
.atomic (write option)
Writes to temp file then renames atomically. File is never partially written — crash-safe.
JSONSerialization
Foundation class for converting between JSON Data and Swift dictionaries. Used in ProfileFileStorage.
FileManager
iOS API for filesystem operations. Used to get the Documents directory URL for saving JSON and JPEG files.
Documents Directory
App sandbox location for user files. iCloud-backed. Stores profile_cache.json and profile_photo.jpg.
Eventual Connectivity
Pattern where the app shows best available data immediately and syncs when connectivity is restored.
ObservableObject
Combine protocol. Objects conforming to it publish changes; SwiftUI views re-render on @Published changes.
@Published
Property wrapper that wraps a value in a Combine Publisher. Triggers SwiftUI view updates on change.
@StateObject
SwiftUI wrapper that creates and owns an ObservableObject. Used in ProfileView to own ProfileViewModel.
@ObservedObject
SwiftUI wrapper that subscribes to an existing ObservableObject. Used in subviews receiving the viewModel.
PhotosPicker
iOS 16+ system photo picker (PhotosUI framework). No permission needed — runs in OS process.
Firebase Firestore
Cloud NoSQL document database. Collections/documents hierarchy. Stores user profile data.
Firebase Storage
Cloud binary file storage (images, videos). Per-user security via Firebase Auth rules.
Firebase Auth
Authentication service. Auth.auth().currentUser?.uid provides the authenticated UID used across the app.
StorageReference
A path in Firebase Storage. Created with Storage.storage().reference().child("path"). Used for putData/downloadURL.
URLSession
Apple's networking API. Used in ProfileImageCache to download images from Firebase Storage URLs.
QoS (Quality of Service)
CPU priority hint for DispatchQueue. .background is lowest — for non-urgent I/O work.
MVVM
Model-View-ViewModel. SwiftUI View observes ProfileViewModel which manages data from Services/Models.
Optimistic Update
Updating the UI immediately before server confirmation. Used for profile photo — shows instantly, uploads in background.
